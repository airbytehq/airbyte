# source-pipedrive: Unique Connector Behaviors

## 1. Core Streams Read API v2 Entity Endpoints; Nothing Reads Recents Any More

`deals`, `deals_archived`, `persons`, `organizations`, `activities` and `products` call `api/v2/<entity>` with `limit=500`, `sort_by=update_time`, `sort_direction=asc` and the shared `definitions.v2_cursor_paginator` (`additional_data.next_cursor` into `cursor`). Their `DatetimeBasedCursor` sends the start date or the saved cursor as the inclusive `updated_since` parameter, formatted `%Y-%m-%dT%H:%M:%SZ`; `cursor_datetime_formats` also lists the fractional RFC3339 form and the legacy `%Y-%m-%d %H:%M:%S` form so state written by 2.x still resumes. `GET /api/v2/deals` returns only not-archived deals, so archived deals are a separate `deals_archived` stream on `/api/v2/deals/archived` with the same parameters and schema; both are parents of `deal_products`, `deal_flow` and `deal_installments`. `pipelines` and `stages` use API v2 but stay full refresh: those endpoints have no `updated_since` parameter and answer HTTP 400 when it is sent.

`notes` and `leads` stay on API v1 and use its inclusive RFC3339 `updated_since` parameter; `files` has no server-side filter (`/v1/files` accepts only `start`, `limit`, `sort`), so it is client-side incremental (`is_client_side_incremental: true`) and re-reads the whole list every sync. All three page with `start`/`limit` offsets sorted by `id ASC` and carry `lookback_window: PT1H`. `GET /v1/leads` returns only leads that are not archived, so archived leads are a separate full refresh stream `leads_archived` on `GET /v1/leads/archived` (no `updated_since` there) with the `leads` schema. `filters` and `users` are unpaginated v1 lists and full refresh. `deal_flow` reads `GET /v1/deals/{id}/flow?items=dealChange&all_changes=1` for every deal returned by `deals` and `deals_archived` and filters the changes client-side on `log_time` (legacy `%Y-%m-%d %H:%M:%S`), with per-parent state (`incremental_dependency: true`).

`deal_products` reads `GET /api/v2/deals/products` with up to 100 `deal_ids` per request (a `GroupingPartitionRouter` over `deals` and `deals_archived`, the pattern `deal_installments` uses); the batch endpoint returns the same items as `/api/v2/deals/{id}/products` and ignores ids it does not know. `product_variations` reads `GET /api/v2/products/{id}/variations` for every product: its parent reuses the `products` retriever without the incremental cursor, so the Start Date does not hide older products. `goals` calls `GET /v1/goals/find` once per `assignee.type` (`person`, `team`, `company`).

With an API token both request bases resolve to `https://api.pipedrive.com/`, the layout the vendor's OpenAPI documents (v1 server `https://api.pipedrive.com/v1`, v2 server `https://api.pipedrive.com/api/v2`), so v2 paths carry the `api/` prefix themselves. Do not move the token base to `https://api.pipedrive.com/api/`: `/api/v1/leads`, `/api/v1/leadLabels`, `/api/v1/leadSources`, `/api/v1/goals/find` and `/api/v1/mailbox/*` answer 404 on that host. With OAuth every request goes to the company host from the token response (`credentials.api_domain`), which serves both versions under `/api/`: `definitions.base_requester` (v1 paths) resolves to `<api_domain>/api/` and `definitions.v2_requester` (the streams with `api/v2/` paths) to `<api_domain>/`. Stream paths are the same for both credentials, so a new stream picks the requester that matches its path prefix.

**Why this matters:** Since 2024-12-01 `GET /v1/recents` returns at most one month of history whatever `since_timestamp` says, and the v1 entity endpoints for deals, persons, organizations, activities, products, pipelines, stages and deal products are out of support since 2026-08-01, so any stream that goes back to them silently loses history or breaks. Keep `datetime_format` on the v2 cursors exactly `%Y-%m-%dT%H:%M:%SZ`: the v2 endpoints reject fractional seconds and space-separated timestamps with HTTP 400 (`cursor_datetime_formats` only parses record values, it never formats requests). Because `updated_since` is inclusive, every incremental run re-emits the record whose `update_time` equals the saved cursor; that is expected and deduplicated on the primary key downstream. The v1 offset streams must keep an immutable sort key: sorted on `update_time`, a record edited during a read moves to the end of the list and the record behind it slides onto a page that was already read, and the state then moves past it for good. The one-hour lookback covers a record edited after the read passed it. Neither helps when a record before the current offset is deleted or archived during a read: the rest of the list shifts back by one and the next page starts one record late, which offset paging cannot prevent. Without an assignee filter `goals/find` returns only the token owner's goals ("When omitted, only your goals will be returned"), and any `assignee.type` returns everyone's goals of that type. A cached parent stream (`deals`, `deals_archived`, `mailThreads`) must not get a multi-value partition router: the CDK shares one sqlite request cache per stream across worker threads and concurrent partitions of the same parent corrupt it ("file is not a database"), which is why archived deals are a second stream rather than a second partition of `deals`.

## 2. API v2 Records Nest Custom Fields and Carry `is_deleted`

API v2 list responses put records under `data` and the next cursor under `additional_data.next_cursor`; the last page omits `next_cursor` or sets it to `null`, and some v2 endpoints omit `additional_data` entirely, so the paginator reads it with null-safe `.get` chains. v2 records use `owner_id` instead of `user_id`, `label_ids` instead of `label`, `is_deleted` instead of `active_flag`/`deleted`, drop the denormalized `*_name`, `*_count` and `next_activity_*` fields, and expose custom values under a nullable `custom_fields` object keyed by the same 40-character hash keys Pipedrive used at the top level in v1. The `*_fields` streams (`deal_fields`, `person_fields`, `organization_fields`, `product_fields`, `activity_fields`) map each hash key to its label and type; join on `key`, which is also their primary key. `leads` and `leads_archived` still come from API v1, which has no v2 list endpoint, so lead custom values arrive as top-level hash keys (leads inherit the deal custom fields).

**Why this matters:** The schemas keep `additionalProperties: true` and declare `custom_fields` as a nullable object without listed properties, because the keys differ per Pipedrive account and can never be enumerated statically. Tightening the schemas, enabling `autoImportSchema` or adding a normalization step would silently drop every custom field. The top-level lead keys cannot be declared either; they are the only undeclared fields a live read returns, which is why `acceptance-test-config.yml` keeps `fail_on_extra_columns: false`. `activities` never returns `custom_fields` even though the schema allows it. The v1 `NullCheckedDpathExtractor` and `components.py` are gone: v2 responses never wrap a record in `{"item": ..., "id": ..., "data": null}`, so a plain `DpathExtractor` on `data` is correct and the connector is manifest-only again.

## 3. Date Fields Are Typed to Their Actual Shape

API v2 timestamps are RFC3339 with a `Z` suffix and are typed `format: date-time` plus `airbyte_type: timestamp_with_timezone`; date-only fields (`expected_close_date`, `local_*_date`, `billing_start_date`, `due_date`) are `format: date`. API v1 timestamps are `YYYY-MM-DD HH:MM:SS` without a zone and are typed `format: date-time` plus `airbyte_type: timestamp_without_timezone` (`notes`, `files`, `filters`, `users`, `activity_types` and the `*_fields` streams). `leads` and `lead_labels` are the v1 exceptions that return RFC3339 with fractional seconds and are typed `timestamp_with_timezone`; `mail` timestamps are `format: date-time` without `airbyte_type`. Fields that hold only `HH:MM` (for example `activities.due_time` and `activities.duration`) stay untyped strings, and so do `deal_flow.old_value` and `new_value`, whose values take the type of whichever field changed (timestamps, dates and plain strings in one column).

**Why this matters:** Typed destinations map `format`/`airbyte_type` to column types, so a wrong pairing (or a strftime pattern such as `"%Y-%m-%d %H:%M:%S"` in `format`, which two `deal_fields` properties carried until 3.0.0) fails schema evolution or produces unparseable values. Adding or changing a `format` on an existing field is a breaking change, so these date-like fields are untyped strings until the next major release: `projects` `add_time`, `update_time`, `archive_time`, `status_change_time`, `start_date`, `end_date`; `tasks` `add_time`, `update_time`, `marked_as_done_time`, `due_date`, `start_date`; the six `mailThreads` timestamps; `call_logs` `start_time` and `end_time` (the vendor gives both an RFC3339 example and a `YYYY-MM-DD HH:MM:SS` description); `legacy_teams.add_time`; `deal_installments.billing_date`; `deal_flow.log_time`; `goals` `duration.start` and `duration.end`; `filters.last_used_time` (no vendor format or example, null on every test-account filter).

**Declared types follow the vendor reference.** Every property's JSON `type` matches Pipedrive's OpenAPI ([v1](https://developers.pipedrive.com/docs/api/v1/openapi.yaml), [v2](https://developers.pipedrive.com/docs/api/v2/openapi.yaml)) and the values a live read returns. Lead ids are UUID strings wherever they appear (`notes.lead_id`, `files.lead_id`, `mailThreads.lead_id`). Use `integer` where the reference constrains a `number` to whole values: an `enum` such as `numberBoolean` (`[0, 1]`) or `visible_to` (`[1, 3, 5, 7]`), or epoch milliseconds such as `message_time`. Use `number` only where fractional values can occur, such as amounts and prices. Check the OpenAPI before changing a declared type: a type change is a breaking change for typed destinations (S3 Data Lake refuses a string column that becomes a list or struct, and any promotion between `double` and `long`) and needs a major version with a migration guide.

Known differences from the reference, kept until a major release because every fix is a type change:

| Field | Declared | Reference | Why it stays |
| --- | --- | --- | --- |
| 28 `enum [0, 1]` flags (mail, mailThreads, legacy_teams), `products.visible_to`, six party `message_time` fields | `integer` | `number` | The reference limits them to whole values |
| `mailThreads.version` | `integer` | `number` | Only the response example (9) shows its values |
| `goals` `owner_id`, `assignee.id`, `expected_outcome.target`, `type.params.pipeline_id[]`, `type.params.activity_type_id[]` | `number` | `integer` | Every value is a whole number and validates today |
| `leads.label_ids`, `mailThreads.drafts_parties` | `array` without `items` | array of uuid strings, array of objects | Adding `items` changes the S3 Data Lake column type |
| `deal_fields.show_in_pipelines` | object with its fields under `items:` | object with `show_in_all` and `pipeline_ids` | Same |

`product_variations.prices[].product_variation_id` is `integer`: the v2 reference types the `prices` items only in prose ("product_variation_id (number)"), and the value is the variation `id`, which it declares `integer`, like `products.prices[].product_id`.

Three fields keep a type list wider than the reference because their values really vary: `deal_fields.mandatory_flag` is a boolean or an object of conditional requirements (keys `status`, `person_id`, `org_id`); `deal_flow.additional_data` is `[]` when empty and otherwise an object with `old_value_formatted` and `new_value_formatted`; `options[].id` on the `*_fields` streams is a string, boolean or integer depending on the field.

## 4. OAuth Is the Default, the API Token Travels in a Header, Old Configs Are Migrated

`definitions.base_requester` (inherited by `v2_requester`) carries a `SelectiveAuthenticator` keyed on `credentials.auth_type`. `oauth2.0` is the first `oneOf` option and is wired to `advanced_auth` for Declarative OAuth: consent at `https://oauth.pipedrive.com/oauth/authorize`, code exchange and refresh at `https://oauth.pipedrive.com/oauth/token` with a Basic `client_id:client_secret` header (the CDK leaves the client credentials out of the refresh body when that header is set), and the token response's `api_domain` is stored in `credentials.api_domain` because Bearer requests must go to the company host ([OAuth guide](https://pipedrive.readme.io/docs/marketplace-oauth-authorization)); its spec `pattern` accepts only `https://<company>.pipedrive.com`, so the token cannot be sent to another host. `api_token` sends the token in the `x-api-token` header, the only way Pipedrive's [authentication guide](https://pipedrive.readme.io/docs/core-api-concepts-authentication) and both OpenAPI specs (`components.securitySchemes.api_key`: `in: header`) document. Two chained `ConfigMigration`s lift the pre-2.0.0 `authorization.api_token` to the top level and then wrap a flat `api_token` into `credentials: {auth_type: api_token, api_token}` (one field per transformation, `value_type: string`); the CDK writes the migrated config back and emits a CONTROL message, so existing connections keep working without user action. The migration copies, so the top-level `api_token` stays in saved configs: the spec keeps it as a hidden `airbyte_secret` so the platform keeps masking it and 4.1.x can still read a migrated config after a rollback. Either credential belongs to a single user, so all streams are scoped to that user's visibility and permission set.

**Why this matters:** Do not put the token back into `request_parameters` (versions before 4.1.0 did, and it put the token in every URL) and do not read `config['api_token']` outside the migrations, because migrated configs only carry `credentials`. `credentials` is deliberately not in the top-level `required` list: the standard spec backward-compatibility test compares with the published spec, cannot see config migrations and reports a newly required property as breaking; each `oneOf` option requires its own fields. The form always fills one option, so only a config created through the API without `credentials` gets past validation; it fails at `check` with a system error (`'dict object' has no attribute 'credentials'`) instead of a config error. In unit tests that go through the entrypoint wrapper, use the `credentials` shape: the wrapper validates the raw config against the spec before the source migrates it. Cloud needs Airbyte's production OAuth app registered for this definition, otherwise the default option asks for client credentials. The app's scopes are listed in CONTRIBUTING.md; a missing one answers 403 `Scope and URL mismatch`, which `error_filters.scope_mismatch` fails as `config_error` on every handler (section 6). OAuth tokens from the pre-2023 connector (0.1.x) are not migrated and need re-authentication. `check` succeeding does not imply the credential can see company-wide data.

## 5. Mail Streams Are Scoped to One User's Mailbox and Fan Out per Folder and Thread

`mailThreads` calls [`GET /v1/mailbox/mailThreads`](https://developers.pipedrive.com/docs/api/v1/Mailbox#getMailThreads) once per folder using a `ListPartitionRouter` over `inbox`, `drafts`, `sent`, and `archive`. `mail` is a substream that calls [`GET /v1/mailbox/mailThreads/{id}/mailMessages`](https://developers.pipedrive.com/docs/api/v1/Mailbox#getMailThreadMessages) for every thread `mailThreads` returns. With an API token these v1 mailbox endpoints are only available under the bare `https://api.pipedrive.com/` host; with OAuth the company host serves them under `/api/v1/` (section 1). Pipedrive's mailbox endpoints only return the mailbox of the connected user.

**Why this matters:** The same thread can be emitted from more than one folder, so `mailThreads` can contain duplicate `id` values within a sync, and `mail` issues one request per thread, which dominates request volume on busy mailboxes. Neither stream can see other users' mail regardless of admin rights. `mailThreads` is the one parent stream with `use_cache: false`: the CDK otherwise caches parent responses in one sqlite file per stream, and the four folder partitions read in parallel corrupt that cache (`sqlite3.DatabaseError`, sometimes a crash), which a direct `mailThreads` read reproduces in the unit tests. The cost is that `mail` fetches the thread list again instead of reading it from the cache.

## 6. HTTP Errors Are Classified on the Shared Base Requester

Every stream `$ref`s `definitions.base_requester`, directly or through `definitions.v2_requester`, which carries `definitions.base_error_handler` (a `DefaultErrorHandler`). Pipedrive returns a JSON envelope `{"success": false, "error": "...", "errorCode": N}` for most failures. Every message template quotes `error` through `(((response if response is mapping else {}).get('error') or '<fallback>') ~ '')[:300]`, so a missing, null or non-text `error`, a non-object body and Cloudflare's HTML 403 still produce a readable message, and the vendor text is capped at 300 characters. The statuses below come from Pipedrive's [HTTP status code reference](https://pipedrive.readme.io/docs/core-api-concepts-http-status-codes) and [rate limiting guide](https://pipedrive.readme.io/docs/core-api-concepts-rate-limiting).

| Status | Pipedrive's meaning | Action | Failure type |
| --- | --- | --- | --- |
| 400 | Request not understood | CDK default: FAIL | `system_error` |
| 401 | Invalid API token or OAuth access token (the message names the credential in use) | FAIL | `config_error` |
| 402 | Company account is not open (trial expired, payment details missing) | FAIL | `config_error` |
| 403 | Request not allowed: permissions, plan limits, or Cloudflare's HTML 403 after repeated rate-limit violations | FAIL | `config_error` |
| 404 | Resource unavailable | CDK default: FAIL | `system_error` |
| 405 | Incorrect request method | CDK default: FAIL | `system_error` |
| 410 | Old resource permanently unavailable | FAIL | `system_error` |
| 415 | Feature is not enabled | FAIL | `config_error` |
| 422 | Webhooks limit reached (webhook creation only; a read-only source never receives it) | CDK fallback | |
| 429 | Rate limit exceeded: burst window or daily token budget | RATE_LIMITED | transient |
| 500, 502, 503, 504 | Server error, scheduled maintenance (503) | RETRY (CDK default; per-stream handlers also retry 505-511 and Cloudflare's 520-527 and 530) | transient |
| 501 | Non-existent functionality | FAIL | `system_error` |

Backoff for RETRY and RATE_LIMITED (`max_retries: 10`): `WaitTimeFromHeader` on `x-ratelimit-reset` (Pipedrive reports a relative number of seconds; there is no `Retry-After`), then `ExponentialBackoffStrategy` with factor 5 when the header is absent. `max_waiting_time_in_seconds: 300` is a kill-switch, not a cap: if the header reports 300 s or more the stream stops with a transient error instead of waiting. Header-less retries are bounded by the CDK's 600 s `max_time`, so they get about seven attempts, not eleven. When retries on a 429 run out, the CDK raises its own message; the Pipedrive-specific hint about the daily budget is in the logs.

`definitions.error_filters` contains the named `HttpResponseFilter`s for scope-mismatch, OAuth-token-rejected, unauthorized, payment-required, forbidden, gone, feature-not-enabled, not-implemented and rate-limited responses. `base_error_handler.response_filters` `$ref`s those nine filters in that order. `scope_mismatch` matches Pipedrive's 403 text `Scope and URL mismatch` (an OAuth app without the scope an endpoint needs) by `error_message_contains` alone, without `http_codes`, because a filter matches on status OR text; it is the first filter of every list, including the per-stream ones below, so a missing scope fails as `config_error` instead of being skipped as a hidden record or an unavailable feature. `oauth_token_rejected` comes second everywhere: the CDK signs a request before the request budget can hold it and treats a token as valid until the exact expiry instant, so an OAuth request can reach Pipedrive with a token that just expired. A JSON 401 (`errorCode` 401) from a host other than `api.pipedrive.com` refreshes the token once and retries; a second rejection fails as `config_error` with the CDK's own text ("Refreshed OAuth access token is rejected by the API", or "OAuth token refresh request is rejected by the token endpoint" when the refresh itself fails); the filter's message only reaches the logs, so the `unauthorized` OAuth text is now the fallback for a 401 without Pipedrive's envelope. The predicate keys on `request_url` (passed to predicates since CDK 7.37.0) because it cannot see the config, so API-token 401s still fail at once through `unauthorized`. The `server_error_retry`, `client_error`, `not_found` and `html_error_page` filters are only for per-stream handlers.

Each per-stream handler `$ref`s `definitions.base_error_handler` and overrides `response_filters`. `$ref` merging replaces `response_filters` wholesale, so every per-stream list must include each base filter it needs; the handler still inherits the base type, `max_retries: 10` and backoff strategies. Order each list most-specific first: `scope_mismatch` and `oauth_token_rejected`, the IGNORE filters that hold whatever the body (plan statuses, the API v1 404s of `legacy_teams` and `permission_set_assignments`), the reachable base filters, `server_error_retry`, `client_error`, `not_found` where the stream does not skip a 404, `html_error_page`, then the skips that must stay JSON-only: the child streams' 404 and 410, the `projects` and `tasks` 404, and every JSON 403. Filters shadowed by an earlier IGNORE are omitted:

- `definitions.substream_missing_parent_error_handler` (used by `deal_flow`, `mail` and `product_variations`) IGNOREs a JSON 404 or 410 for a parent deleted or merged after the parent read, and a JSON 403 for a parent the connected user cannot see.
- `deal_products` does not skip 404 or 410 because the batch endpoint answers 200 for deal ids it no longer has (404 keeps the CDK default through `not_found`); a JSON 403 skips the batch of up to 100 deals.
- `legacy_teams`, `projects`, `tasks` and `deal_installments` IGNORE the plan or feature responses listed for each endpoint (`legacy_teams`: 415 only), then JSON 403; `projects` and `tasks` skip a 404 only when it is JSON, and `legacy_teams` and `deal_installments` keep the CDK default for 404 through `not_found`. `legacy_teams` fails a 410 through `gone`: Pipedrive documents neither 404 nor 410 for that deprecated endpoint, so its retirement must fail the sync rather than empty the stream. `permission_set_assignments` IGNOREs its documented 404 for a permission set without assignments and JSON 403.

`server_error_retry` (408, 500, 502-504, no message, so the CDK mapping keeps its text) and `gateway_error_retry` (505-511 and Cloudflare's 520-527 and 530, with a message that keeps Pipedrive's body once retries run out) repeat the CDK default retry on purpose: they must precede `html_error_page`, so an HTML maintenance or gateway page is retried rather than failed. `client_error` (400, 405) and `not_found` (404) carry no message, so the CDK default classification applies (FAIL, `system_error`); they precede the guard for the same reason. `html_error_page` fails any `text/html` response as `config_error` with its own message. Pipedrive answers with HTML for Cloudflare's 403 block after repeated rate-limit violations and for an API v2 route it does not know: checked live on 2026-10-23, `GET /api/v2/nonexistent-endpoint` returns an HTML 404 page, while a missing record returns JSON (`Entity not found.` on `/api/v2/products/{id}/variations`, `Deal not found` on `/v1/deals/{id}/flow`). The guard must follow every status-specific filter because the CDK predicate sees the parsed body and headers, never the status; a filter matches when its status is listed OR its predicate matches. The JSON-only skips follow the guard, so an API v2 route that Pipedrive stops routing (an HTML 404) fails the sync instead of emptying `product_variations`, `projects` or `tasks`; a retirement answered with a JSON 404 or 410, or a retired API v1 child route, still reads as a missing parent. Other HTML responses that reach the guard also fail: an HTML 2xx or 3xx is no longer read as an empty page, an HTML 4xx outside the mapped statuses (409, 422, ...) and an HTML 5xx outside the two retry filters (512-519, 528, 529, 531-599) fail once instead of the CDK fallback retry. The guard fails as `config_error`, which the certified-connector success-rate monitor excludes, so a retired API v2 route on `product_variations`, `projects` or `tasks` shows up as failed syncs rather than as a monitor alert; on `deal_products` and `deal_installments` the same 404 is a `system_error` through `not_found`. Tests must not assert on retry log text, which comes from the CDK or the backoff library and changes between versions.

## 7. One Shared Request Budget and a Small Thread Pool

The manifest declares a top-level `api_budget` (`HTTPAPIBudget` with one `MovingWindowCallRatePolicy`: 20 requests per rolling 2 seconds) and a `concurrency_level`. The policy's `HttpRequestRegexMatcher` matches on the URL path (`^(/api)?/v[12]/`), not on the host, so it covers `https://api.pipedrive.com/v1/...`, `/api/v2/...` and the per-company hosts that OAuth uses. 20 per 2 seconds is the API-token burst limit of Pipedrive's lowest plan ([docs](https://pipedrive.readme.io/docs/core-api-concepts-rate-limiting); 20, 40, 100 or 120 by plan); the plan is not knowable from the config, so the floor is used. `ratelimit_remaining_header` is `x-ratelimit-remaining`: when Pipedrive reports zero calls left, the CDK (7.29 and later) drains the bucket until the window rolls. `x-ratelimit-reset` is deliberately not declared on the policy: the CDK syncs the bucket only when no reset header is configured, and Pipedrive sends a relative number of seconds where the CDK expects an epoch timestamp.

Pipedrive's other limit is a daily token budget of "30,000 base tokens x subscription plan multiplier x number of seats" (plus purchased top-ups), shared by every API token and OAuth app in the company and reset at midnight server time; once spent, every request answers 429. Each request costs the `x-token-cost` the OpenAPI lists: 20 for most v1 lists (40 for `deals/{id}/flow` and `leads/archived`, 10 for `leadLabels`, 2 for `leadSources`), 10 for most v2 lists (20 for `deals/archived`, 5 for `pipelines` and `stages`). The streams that fan out per parent multiply these on every sync: `deal_flow` costs 40 tokens per deal, `mail` 20 per mail thread, `product_variations` 10 per product (every product on every sync, since the stream is full refresh and its parent has no cursor), and `deal_products` and `deal_installments` 10 per 100 deals. Responses carry `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset`, `x-daily-ratelimit-token-limit` and `x-daily-ratelimit-token-remaining`. No stream calls the Search API, whose separate limit (10 requests per 2 seconds) therefore does not apply.

`default_concurrency` is `[config.get('num_workers') or 3, 2] | max` with `max_concurrency` 10. The `num_workers` spec field keeps `minimum: 1` for saved configs, but a value of 1 runs with 2 workers: with one worker the CDK's partition generator holds the only thread and a substream with many parents waits forever (`ConcurrentDeclarativeSource._LOWEST_SAFE_CONCURRENCY_LEVEL = 2`). Versions 2.3.0 to 2.3.7 allowed up to 40 workers; a config migration lowers a saved value above 10 to 10 before the spec validates it.

**Why this matters:** Every stream shares the one budget, so more workers never exceed the burst limit and rarely make a sync faster. The daily budget has no policy on purpose: its plan multiplier, seats and top-ups cannot be known from the config, other integrations in the company spend it too, and the CDK budget reads a single remaining header. Do not add per-stream budgets or a second policy; tune the single `Rate` if the floor ever changes. Parent streams that the CDK caches (`deals`, `deals_archived`) share one HTTP session across their children, so keep `max_concurrency` modest; `mailThreads` opts out of the cache for the reason given in section 5.

`maxSecondsBetweenMessages` is 10800. The platform's heartbeat resets on every RECORD and STATE message, so the longest silence is a run of requests that return nothing. A single request waits at most for ten retries bounded by the 300 s kill switch and the CDK's 600 s `max_time`. `deal_products` asks for 100 deals per request at no more than 10 requests per second, so three hours of silence would take more than ten million deals without products. `product_variations` makes one request per product, so it would take more than 100,000 products without variations. `deal_flow` emits STATE as its per-deal partitions close, and every deal has at least its creation event. Re-derive the value before adding a stream that fans out per parent.

## 8. Deletions Are Replicated for Deals and Projects

`deals` and `deals_archived` request `status=open,won,lost,deleted`, so deals deleted within the last 30 days arrive with `is_deleted: true`; Pipedrive does not return older deletions. `projects` (both `projects` and `projects/archived`) requests `status=open,completed,canceled,deleted` (the documented status list, example `open,completed`), so deleted projects arrive with `status: deleted`. No other stream requests deleted records: the `is_deleted` field on other v2 records and on `users` is passed through exactly as returned and is not a deletion feed, and the full refresh streams re-read the live collection. Archived leads arrive through `leads_archived`, not as deletions. Child streams tolerate a parent deleted between the parent read and the child request through their error handlers (section 6).

**Why this matters:** Destinations keep rows for records deleted in any stream other than `deals`/`deals_archived` and `projects` until the user clears the stream, and the docs say so. Do not describe `is_deleted` on persons, organizations or products as deletion replication, and do not add `status=deleted` style parameters to streams whose endpoint does not document them.

## 9. Every List Endpoint's Pagination Is Recorded

Pipedrive's [pagination guide](https://pipedrive.readme.io/docs/core-api-concepts-pagination) describes cursor pagination for API v2 and `start`/`limit` offsets for API v1, but the per-endpoint reference decides: several v1 lists ignore `start` and `limit` entirely, and some cap the page below 500. Checked on the test account on 2026-10-12 by sending each endpoint its documented maximum:

| Mechanism | Page size | Streams (endpoint) |
| --- | --- | --- |
| v2 cursor (`additional_data.next_cursor` into `cursor`) | `limit=500` (the documented maximum; 501 answers 400) | `deals`, `deals_archived`, `persons`, `organizations`, `activities`, `products`, `pipelines`, `stages`, `deal_products`, `deal_installments`, `product_variations`, `projects`, `tasks` |
| v1 offset (`additional_data.pagination.next_start` into `start`) | `limit=500` (served 500) | `deal_fields`, `activity_fields`, `organization_fields`, `person_fields`, `product_fields`, `roles`, `leads`, `leads_archived`, `notes`, `deal_flow`, `permission_set_assignments` |
| v1 offset | `limit=100` (`/v1/files` documents and serves at most 100) | `files` |
| v1 offset | `limit=50` (`/v1/callLogs` answers 400 above 50; `/v1/mailbox/mailThreads` serves 50 when asked for 500) | `call_logs`, `mailThreads` |
| Unpaginated in the reference, v1 offset paginator kept in case Pipedrive pages it (it stops when `next_start` is absent) | `limit=50` | `mail` ("Returns all the mail messages inside a specified mail thread"; the test account has no mail to confirm it) |
| Unpaginated in the reference (no `start` or `limit`); with `limit=1` the test account still returned every item | `limit=50` on `currencies`, `activity_types`, `lead_labels`, `permission_sets` and `goals` (ignored); none on the rest | `currencies`, `filters`, `users`, `activity_types`, `lead_labels`, `lead_sources`, `permission_sets`, `goals`, `legacy_teams` (answers 403 on the test account) |

The v1 reference documents a flat `additional_data` (`start`, `limit`, `more_items_in_collection`) for `GET /v1/leads` and `GET /v1/leads/archived`, but on 2026-10-14 both answered with `additional_data.pagination` like the other v1 lists, and `/v1/leads` with `limit=1` returned `next_start` 1, then 2. Keep the nested expression on both streams.

**Why this matters:** A stream without a paginator, or with a page size below what the endpoint serves, still finishes `COMPLETE`: the first returns one page and loses the rest silently, the second only costs requests and daily tokens. Re-check an endpoint's maximum against the reference and one live request before changing its `limit`. A round number of records on an unpaginated stream is not a short read by itself: `filters` returned exactly 50 on the test account, and `limit=500` and `start=50` returned the same 50 ids.
