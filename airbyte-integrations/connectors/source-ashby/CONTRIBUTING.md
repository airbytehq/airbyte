# Contributing to source-ashby

For general guidance on contributing to Airbyte connectors, see the [Connector Development documentation](https://docs.airbyte.com/connector-development/).

## Incremental Stream Considerations

The Ashby API uses `.list` endpoints with cursor-based pagination. The `applications` and `interview_schedules` endpoints support `createdAfter` filtering, but since these resources are mutable (status changes, updates), `created_at`-only filtering is insufficient for true incremental sync. `application.list` doesn't document `updatedAfter` ([reference](https://developers.ashbyhq.com/reference/applicationlist)), and a live probe (2026-09-30) showed it is silently ignored: a request with `updatedAfter` set to the current time still returned applications last updated in 2022, while `createdAfter` filtered as documented. All other `.list` endpoints (candidates, jobs, offers, etc.) do not document date-based filtering.

### Future incremental stream candidates

- **No `syncToken` or date filter (6 streams):** `archive_reasons`, `interview_stage_groups`, `interview_stages`, `job_boards`, `job_postings`, `sources` — these endpoints' request schemas expose neither `syncToken` nor a date filter, so they stay full refresh.
- **`applications`:** `application.list` accepts `syncToken`, but the stream already persists `updatedAt` datetime state (also read by `application_history` through `incremental_dependency`). Moving it to `SyncTokenCursor` changes its state format with no possible state migration (a token cannot be derived from a timestamp), so it is deferred to a separate change.

## Authentication, Rate Limits, and Sync Tokens

- **Authentication:** Ashby's public API authenticates only with API keys (HTTP Basic, key as username, blank password) and offers no OAuth flow — see the [Ashby authentication reference](https://developers.ashbyhq.com/reference/authentication).
- **Rate limits:** Ashby documents 1,000 requests per minute per API key ([source](https://docs.ashbyhq.com/how-do-i-generate-an-api-key)). `concurrency_level` reads up to two streams at a time (`default_concurrency: 2`), and `api_budget` throttles only the per-application partitioned endpoints (`application.listHistory` and `application.listCriteriaEvaluations`, 100 requests/minute each). All other streams rely on the shared error handler's backoff on HTTP 429 (`Retry-After` header first, then exponential).
- **Error envelope:** Ashby returns most errors as HTTP 200 responses with `success: false` and an `errorInfo` object; these are surfaced by the shared `definitions.error_handler`, which every requester references. `application_history` and `application_criteria_evaluations` override its `response_filters` with the shared `definitions.response_filters` entries plus an `application_not_found` IGNORE ahead of the generic FAIL, because a sibling `response_filters` key replaces the referenced list rather than extending it.
- **Sync tokens:** Every stream whose endpoint request schema accepts `syncToken` (all of them except `applications`, which keeps its `updatedAt` cursor) uses the shared `definitions.sync_token_cursor` (`SyncTokenCursor`) from released `airbyte-cdk` 7.41.0. Ashby returns a new `syncToken` only on the page with `moreDataAvailable: false` and echoes the request's token on earlier pages, so the committed token is sent in the request body on every page alongside `cursor`, and a new token is committed only when the pass completes. Two response filters fail rejected tokens with `config_error` and keep the stored token, with the code read from `errors[]` (strings or `{code}` objects) or `errorInfo.code`. `sync_token_rejected` handles `sync_token_expired` (the token is older than Ashby's 14-day validity) and `sync_token_invalid` (the token can't be decoded) and tells the user to refresh the stream, which clears its state so the next sync re-reads it in full. `incremental_sync_too_large` has its own filter and message. It isn't about time windows, since these streams have none: it means more records changed since the stored token was issued than Ashby will page through incrementally, currently 100 pages, or 10,000 records at the connector's page size of 100, and Ashby names bulk data migrations as the usual cause. Because the limit counts changes since the token, retrying with the same token keeps failing as changes accumulate, so the message tells the user to switch the stream to Full Refresh, or to refresh it and sync more often (at least daily). Ashby doesn't document which page of a pass returns this error, so records from earlier pages may be emitted before the stream fails; they're re-read after a refresh because no new token was committed. The filters fail rather than `IGNORE` because an `IGNORE` would keep the token and read nothing on every later sync. Tokens are opaque and never compared or derived from records; `cursor_field: updatedAt` is advertised only for destination deduplication on streams whose records carry it. `createdAfter` alone is not a viable cursor because these resources mutate after creation.
