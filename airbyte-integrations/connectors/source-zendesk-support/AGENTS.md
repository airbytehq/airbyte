# source-zendesk-support: Unique Connector Behaviors

## 1. `tickets`, `users`, `organizations` and `articles` Walk Sorted List Endpoints Newest-First and Stop Themselves

Zendesk stops serving its Incremental Export APIs (`/api/v2/incremental/...`) to third-party integrations between 2026-12-02 and 2027-01-19 ([announcement](https://support.zendesk.com/hc/en-us/articles/11275429993498), [developer guide](https://developer.zendesk.com/documentation/marketplace/building-a-marketplace-app/incremental-third-party/)); blocked requests get a `403`. Since 6.0.0 nothing in the manifest calls an `incremental/` path. The four former export streams share `sorted_list_stream` / `sorted_list_incremental_sync` / `sorted_list_paginator`: each reads its list endpoint sorted by the cursor field descending (`GET /api/v2/tickets?sort=-updated_at`, `/users?sort=-updated_at&include=identities`, `/organizations?sort=-updated_at`, `/help_center/articles?sort_by=updated_at&sort_order=desc`), 100 records per page with cursor pagination, and the paginator's `stop_condition` ends the walk as soon as the last record on a page is older than `stream_slice.start_time`. A `record_filter` drops the older records on that final page, the cursor is a unix-timestamp string as before, and `lookback_window: PT1H` re-reads the hour before the cursor. There is one partition and no `step`, because every slice would have to start from the newest record anyway. `user_identities` is not a separate request: `include=identities` sideloads each page's identities and the stream reads them from the same response, so it can return identities of users whose own `updated_at` is older than the cursor.

The `tickets` cursor changed from `generated_timestamp` (the export's key, bumped on every change including silent system updates) to `updated_at` (what the list can sort by, bumped only for changes that generate a ticket event). `TicketsStateMigration` in `components.py` converts a saved `generated_timestamp` value into `updated_at` minus one hour, and the CDK runs the same migration on the `parent_state` of every substream whose parent is `tickets`. The migration never advances the cursor and is skipped for state that already has `updated_at`. The list endpoints exclude archived tickets (archived about 120 days after closing), deleted tickets, deleted users and deleted organizations, which the exports returned; `ticket_metric_events` without a `ticket_id` are unreachable too. These are documented as breaking in 6.0.0; the per-ticket substreams reach archived tickets through a second, search-based parent (section 7).

**Why this matters:** the `stop_condition` is the only thing bounding a sync. It reads `stream_slice` inside the paginator (supported by the CDK), so a change to the sort order, to `page[size]`, or to the record filter without the matching change in the stop condition either re-walks the whole account every sync or silently drops records. An update that changes only `generated_timestamp` is invisible to these streams by design; do not reintroduce a `generated_timestamp` cursor, since no remaining endpoint can filter on it. Any new policy matching `^/api/v2/tickets` must keep the 100 requests per minute budget on the list and must not catch the per-ticket paths.

## 2. StateDelegatingStream for Ticket Metrics — Two Completely Different Sync Paths

The `ticket_metrics` stream uses `StateDelegatingStream` to choose between two completely different retrieval strategies based on whether stream state exists:

**Without state (initial sync / full refresh) — `StatelessTicketMetrics`:**
Queries the bulk `GET /ticket_metrics` endpoint, which returns records sorted by `created_at` descending (newest first). However, the cursor field is `updated_at`, not `created_at`. Because the sort order doesn't match the cursor field, the stream **must read all records** and cannot checkpoint mid-stream (checkpointing would create state, which would switch to the stateful path on the next page). The stream tracks the most recent `updated_at` value across all records and converts it to a unix timestamp saved as `_ab_updated_at` in state:
```json
{ "_ab_updated_at": 1728670522 }
```

**With state (incremental syncs) — `StatefulTicketMetrics`:**
Uses a two-step approach: first walks the `tickets` stream (the ticket list sorted by `updated_at`, see section 1) to get the tickets updated since the parent state, then fetches `GET /tickets/{ticket_id}/metrics` for each ticket. This is more efficient for small deltas but makes one API call per updated ticket. The parent ticket's `generated_timestamp` (which the list still returns, via `extra_fields`) is converted to the `_ab_updated_at` state cursor to maintain consistency with the stateless path, while the nested `parent_state` holds the parent's `updated_at` cursor.

**Why this matters:** The synthetic `_ab_updated_at` cursor bridges two fundamentally different data flows. The stateless path is efficient for initial bulk loads but cannot checkpoint. The stateful path scales linearly with the number of updated tickets — efficient for small incremental syncs but disastrous if state is reset and it tries to re-read all tickets one by one. Understanding which path is active (based on state presence) is critical for diagnosing performance issues.

## 3. Enterprise-Only Streams Disabled at Manifest Level

Several streams (`ticket_forms`, `account_attributes`, `attribute_definitions`) are commented out in the manifest because they require Zendesk Enterprise plans and the CDK does not yet support `ConditionalStreams` based on API endpoint availability. The `ticket_forms` stream definition exists but will FAIL with a descriptive error on 403/404 rather than being silently skipped.

**Why this matters:** These streams cannot be enabled without CDK changes to support conditional stream availability. If a user on an Enterprise plan expects these streams, they will not appear in the catalog at all despite the stream definitions existing in the manifest.

## 4. `ticket_events`, `ticket_comments` and `ticket_metric_events` Are Per-Ticket Substreams That Rebuild the Export Record Shape

All three were Incremental Export streams before 6.0.0. They are now substreams with two parents through the shared `per_ticket_partition_router`: the `tickets` walk and `closed_tickets_search_stream`, an Export Search Results walk (`GET /api/v2/search/export?filter[type]=ticket&page[size]=1000&query=updated_at>=<slice start> status:closed`) with its own `updated_at` cursor that lists the closed tickets, archived ones included, updated since that cursor (section 7 explains why). With `incremental_dependency: true` and `global_substream_cursor: true`, every ticket either parent returns costs one request per stream (`GET /tickets/{ticket_id}/audits.json` for `ticket_events` and `ticket_comments`, which share `per_ticket_audits_retriever` with `ticket_audits_per_ticket`; `GET /tickets/{ticket_id}/metric_events` for `ticket_metric_events`). `ticket_events` and `ticket_comments` keep their cursors (`timestamp` for `ticket_events`, `created_at` for `ticket_comments`, unix-timestamp strings, through `per_ticket_incremental_sync`) but never filter on them: a changed ticket re-emits its whole audit history, because the global cursor is not the time a given ticket was last read (a ticket updated while the walk runs moves ahead of the walk, is first seen a sync later, and a filter on the global cursor minus the lookback would drop the audits it gained in between, for good). `side_conversations` keeps its `updated_at` cursor and, since 6.0.0, bounds its record filter on `start_date` only for the same reason; before 6.0.0 the ascending export reached such a ticket in the same sync. Their state migration is parent-side: for every parent missing from `parent_state`, the CDK factory seeds the parent's state from the child's flat legacy value or global cursor, keyed on the child's cursor field. For `tickets` the CDK re-keys it onto `updated_at`, a valid lower bound; for the search parent, `ClosedTicketsSearchStateMigration` re-keys the seeded value onto `updated_at` minus one hour (the same path handles a 5.7.0 `ticket_audits_per_ticket` state whose `parent_state` has `tickets` only). `ticket_metric_events` cursors on `_ab_updated_at` (the parent's `generated_timestamp`, like `ticket_audits_per_ticket`) and has no record filter: a changed ticket re-emits its whole metric event history. Its former cursor, the event `time`, is unusable: Zendesk dates SLA `breach` events with the future breach moment, a concurrent cursor stores the highest record value it saw regardless of the slice end, and once that value is ahead of the clock by more than the lookback window the CDK yields no slice at all, so the child reads nothing while `parent_state` still advances past the tickets. `TicketMetricEventsStateMigration` turns a 5.x `{"time": ...}` state into `_ab_updated_at` plus a `parent_state` for both parents, clamping a future value to the migration time (the factory reads the migrated state, which is no longer flat, so the CDK's own seeding would not run); `TicketsStateMigration` handles a nested `parent_state` that still carries `generated_timestamp`.

The record shapes mimic the exports:

- `ticket_events` records are audits with `AddFields`/`RemoveFields`: `child_events` = the audit's `events`, `updater_id` = `author_id` (`-1` for Zendesk-made audits, where the export sometimes named a user), `timestamp` = unix `created_at`, `via` = `via.channel` (the export used labels such as `Web form`), `system` = a projection of `metadata.system` onto the export's four keys (`client`, `latitude`, `location`, `longitude`), `event_type` = `Audit`; `author_id` and `events` are removed and the full `metadata` object stays. The child events keep the Ticket Audits shape (`type`, `field_name`, `value`, plus `Notification`/`AgentMacroReference` events the export omitted); there is no mapping back to the export's `event_type` and per-field keys.
- `ticket_comments` uses `ZendeskSupportAuditCommentsExtractor` (`components.py`): the `Comment` events of each audit, enriched with the audit's `ticket_id`, `created_at`, `timestamp`, `via`, `event_type: Comment` and a null `via_reference_id` (the old extractor always emitted null there too). The spec's `page_size` (`Page Size (ticket_comments)`) is applied to the audit pages, clamped to Zendesk's maximum of 100.
- `ticket_metric_events` reads a response keyed by metric name (`{"agent_work_time": [...], "reply_time": [...]}`) with a `DpathExtractor` on `["*", "*"]` and no pagination; the records have the export's fields including `deleted`, plus `_ab_updated_at`.

**Why this matters:** the per-ticket cost is linear in the number of updated tickets, so a bulk update multiplies the request count by three (plus `ticket_metrics`, `side_conversations` and `ticket_audits_per_ticket` when selected) against the account-wide rate limit, with no `api_budget` policy slowing it. The search parent walk runs under the `^/api/v2/search/export(\.json)?$` policy (100 requests per minute, shared with `tickets_search`), once per selected stream per sync, and Zendesk expires a search cursor after about an hour, so nothing may slow that walk below the budget. Overriding `record_selector` on a `$ref` of `per_ticket_audits_retriever` replaces the whole selector (sibling overrides are shallow merges), so a new stream on that retriever must restate the extractor and the record filter. Changing a mapped `ticket_events` field is a breaking change for downstream filters; the `via` label-to-channel mapping is documented in the migration guide. Never give a per-ticket substream a record cursor that can lie in the future (metric event `time`, SLA target timestamps): the global cursor follows record values, not slice ends, and a future value silently empties the stream on the next syncs.

## 5. Per-Ticket Substreams Must Key Error Handling on the Status Code, Not the Response Body

`side_conversations`, the stateful `ticket_metrics` path, `ticket_metric_events` and the three streams built on the shared `per_ticket_audits_retriever` (`ticket_audits_per_ticket`, `ticket_events`, `ticket_comments`) all request one URL per parent ticket (`GET /tickets/{ticket_id}/side_conversations`, `GET /tickets/{ticket_id}/metrics`, `GET /tickets/{ticket_id}/metric_events`, `GET /tickets/{ticket_id}/audits.json`). All of them use IGNORE filters keyed exclusively on `http_codes`, and that is deliberate on two counts:

1. **Zendesk does not guarantee a response body.** Permission denials from the `collaboration-api` service arrive as a `403` with an empty `text/html` body. `HttpResponseFilter._response_contains_error_message` parses the body with `JsonErrorMessageParser`, which yields nothing for a non-JSON body, so an `error_message_contains` filter silently never matches. The same emptiness makes `{{ response.get('error') }}` render as `None` in any error message template.
2. **Denial is scoped to the ticket, not to the stream.** Side conversations require the Collaboration add-on and can be restricted per brand and per group, and a ticket can be deleted between the parent page that listed it and the child request. So individual tickets are refused (`403`) or gone (`404`) while the rest of the stream reads normally. Failing the sync on one refused ticket blocks the whole stream.

There is a second-order trap here. Because these are substreams with `incremental_dependency: true`, the parent cursor is only checkpointed once the substream finishes. A refusal that fails the stream therefore prevents `parent_state` from ever advancing, so the next sync restarts the parent walk from the same position and fails on the same ticket forever — no self-healing, and heavy rate-limit pressure from re-walking the parent every run.

**Why this matters:** the shared `definitions.retriever.requester.error_handler` treats `403`/`404` as a whole-stream configuration error, which is correct for stream-level endpoints and wrong for per-partition ones. Any new substream that requests one URL per parent record needs its own status-code-keyed handler; inheriting the shared one lets a single unreachable parent record fail the sync. Note that `error_message_contains` is also unreliable in the shared handler for the same body-shape reason.

## 6. `num_workers` Minimum Is 2 — One Thread Leaves No Sibling to Beat the Heartbeat

The floor is enforced in three places, and all three are load-bearing:

1. the spec pins `num_workers` to `minimum: 2`;
2. `spec.config_normalization_rules` carries a `ConfigMigration` that rewrites a stored `num_workers: 1` to `2`;
3. `concurrency_level.default_concurrency` clamps with `{{ [config.get('num_workers', 4), 2] | max }}`.

The clamp is not redundant with the migration. In CDK 7.23.8 and later (unfixed as of 7.28.3, tracked in [airbyte-python-cdk#1147](https://github.com/airbytehq/airbyte-python-cdk/issues/1147)) `ConcurrentDeclarativeSource.__init__` builds the `ConcurrencyLevel` component from the **pre-migration** config (`config=config or {}`, not `self._config`), so on the first sync after an upgrade a stored `1` would still run a single worker — exactly the sync that needs two. Verified locally: with a stored `num_workers: 1`, `self._config['num_workers']` is `2` while the thread pool is built with `max_workers=1`. The clamp makes the floor effective immediately; the migration keeps the persisted config consistent with the spec minimum. If the CDK is fixed to interpolate the migrated config, the clamp becomes redundant but stays harmless.

Unclamped, `default_concurrency` is `config.get('num_workers', 4)`, so `num_workers: 1` makes the concurrent framework run a single worker thread and every stream is processed strictly one at a time. The `tickets` stream is the problem case: it walks the ticket list newest-first (section 1) under an `api_budget` of 100 requests per minute (10 per minute on the Incremental Ticket Export before 6.0.0), and its `sorted_list_incremental_sync` has no `step` and no `end_datetime`, so the whole date range is a single partition. The concurrent cursor only emits state when a partition closes, so a long `tickets` walk produces no state message until it finishes.

The platform heartbeat resets on a RECORD **or** a STATE message. With two or more workers, a sibling stream keeps emitting during the walk and the sync stays alive. With one worker there is no sibling: once `tickets` is past its first pages, nothing is emitted at all, and the platform cancels the attempt at the `heartbeat-max-seconds-between-messages` threshold (5400s on Cloud). Because the partition never closes, no cursor is checkpointed, so every retry re-enters the identical state and the connection is wedged permanently rather than making partial progress.

What `airbytehq/oncall#13250` establishes is narrower than the mechanism above: every wedged connection ran 1 thread, and one thread leaves no sibling stream to keep the heartbeat alive during the `tickets` walk. Why that walk runs beat-free long enough to trip the threshold is not confirmed (the sync logs carry no source stdout), and a second worker only helps while sibling streams still have work. Treat the floor as a mitigation, not as the root-cause fix.

**Why this matters:** the failure looks unrelated to concurrency — the heartbeat error names whichever stream happens to be queued (often `group_memberships`), not `tickets`, and the sync logs carry no source stdout. Adding a `step` to `tickets` is not an alternative fix: the list is always read from the newest ticket down to the slice start, so each slice re-walks to the present and duplicates records. See `airbytehq/oncall#13250`.

## 7. `ticket_audits_per_ticket` Is Opt-In, Shares the Per-Ticket Audits Retriever, and Reaches Archived Tickets Through a Search Parent

`ticket_audits` reads `GET /api/v2/ticket_audits`, which Zendesk documents as excluding archived tickets (closed tickets are archived about 120 days after they close) and as unsuitable for change data capture. `ticket_audits_per_ticket` was added in 5.7.0 to read `GET /api/v2/tickets/{ticket_id}/audits.json` for each ticket the Incremental Ticket Export returned, because that export listed archived tickets when they changed and the per-ticket endpoint serves their audits. Since 6.0.0 the ticket list (section 1) omits archived tickets, so `per_ticket_partition_router` (shared with the section 4 streams) has a second parent, `closed_tickets_search_stream`: an Export Search Results walk (`GET /api/v2/search/export?filter[type]=ticket&page[size]=1000&query=updated_at>=<slice start> status:closed`, `sorted_list_incremental_sync` with its own `updated_at` cursor and `PT1H` lookback, `links.next` pagination). Only closed tickets get archived and a closed ticket cannot change status, so `status:closed` narrows the walk to the population the list cannot serve without losing a ticket, and the cursor bounds it to the tickets changed since the previous sync instead of every closed ticket on the account. Archiving does not change `updated_at` or `generated_timestamp` (verified on the test account), so a ticket is not re-read when it is archived; a bulk update of archived tickets is, which is the case this stream exists for. Closed tickets that are not archived yet are listed by both parents: `ConcurrentPerPartitionCursor` skips a duplicate partition only while the first copy is still in flight, so such a ticket can be read twice in one sync. The search index lags a few minutes (hence the lookback), and only the ticket list comes from it; the audits are read live. `ticket_audits` was deliberately left unchanged.

How it is built, and why:

1. **Opt-in through stream selection only: no spec flag, no `ConditionalStreams`.** The stream is always discovered, like every other stream. It is left out of `metadata.yaml` `suggestedStreams`, so a new connection does not select it by default, and an existing connection only starts syncing it when the user selects it or the connection automatically enables new streams. That auto-enable case is the one users must act on, so the user docs and changelog warn about it.
2. **Global substream cursor.** The cursor mirrors the stateful `ticket_metrics` path (`_ab_updated_at` = the parent ticket's `generated_timestamp`, via `extra_fields` and `AddFields`), but `global_substream_cursor: true` stores one cursor value instead of one entry per ticket. Each changed ticket re-emits all of its audits; `id` deduplicates them downstream.
3. **Shared retriever.** `per_ticket_audits_retriever` (requester, status-code-keyed error handler, `links_next_paginator`, `["audits"]` extractor and `per_ticket_partition_router`) is shared with `ticket_events` and `ticket_comments` (section 4); `ticket_metric_events` shares the router only. `extra_fields: generated_timestamp` is declared on the shared router and only this stream reads it.
4. **No `api_budget` policy of its own.** Like the per-ticket `ticket_metrics` calls, `^/api/v2/tickets/\d+/audits` matches no policy, so requests go out at the connector's concurrency and count against the account-wide plan limit shared with other integrations. On a `429` the error handler waits for `Retry-After` (`WaitTimeFromHeader`). The parent walks are separate passes over the ticket list and over Export Search Results, each under its endpoint's 100 requests per minute policy. Do not add a broad policy that matches `^/api/v2/tickets/` without deciding what it does to this stream, `ticket_metrics`, `ticket_events`, `ticket_comments` and `ticket_metric_events`.
5. **Pagination** reuses `links_next_paginator` (`page[size]=100`, `links.next`, `meta.has_more`). A response without `meta.has_more` stops after one page.
6. **Schema** `schemas.ticket_audits_per_ticket` `$ref`s each `ticket_audits` property and adds `_ab_updated_at`. A unit test fails if `ticket_audits` gains a property this schema does not list.

**Why this matters:** do not add the stream to `suggestedStreams`. That would select it on every new connection, exposing users who never asked for it to a request per updated ticket, and a single bulk update can mean six-figure request counts on the next sync. The first sync after the stream is selected reads every ticket since `start_date`, archived ones included. Its reach into archived tickets depends on the `status:closed` search parent: do not drop that parent, and do not widen its query to every ticket, which would re-list the account's recent changes through the stale search index and double every per-ticket read.

## 8. OAuth Completion Must Extract `expires_in` to Persist Token Expiry

Zendesk OAuth uses **rotating, single-use refresh tokens** — each refresh returns a new refresh token and invalidates the previous one. The connector authenticates with `DeclarativeSingleUseRefreshTokenOauth2Authenticator` (via `refresh_token_updater`), which decides whether to refresh by comparing `credentials.token_expiry_date` against now. When that field is empty/absent, the CDK treats the token as already expired (`now - 1 day`) and refreshes on the very first `check`.

Because of this, the `oauth_connector_input_specification.extract_output` list **must include `expires_in`**. The platform's declarative OAuth handler only converts the token response into a persisted `token_expiry_date` when `expires_in` is among the extracted fields. Without it, `token_expiry_date` is never written to the config, so every `check`/`discover`/`read` triggers an immediate refresh — consuming the freshly minted single-use refresh token and (in setup/check lifecycles that don't persist the rotated token) leaving the stored config holding an already-invalidated token, which fails with `invalid_grant`.

The authorization-code exchange (`access_token_url`) **must also request `expires_in=172800` explicitly**. Per Zendesk's docs, passing `expires_in` on token creation is what causes a refresh token to be issued at all, so requesting it makes the field's presence in the response a guarantee rather than an assumption — `DeclarativeOAuthSpecHandler.processOAuthOutput` throws `Missing '<key>' field in the OAuth Output` for any `extract_output` field absent from the response. It also pins the access-token lifetime at 48h (matching `refresh_request_body.expires_in` in `oauth_refresh_authenticator`) instead of Zendesk's ~30-minute default for clients created on/after 2026-04-30, closing the setup-time window where a user takes longer than the token lifetime between authorizing and saving the source.

**Why this matters:** Removing `expires_in` from `extract_output` (or from the `access_token_url` request) reintroduces the premature-refresh loop. See `airbytehq/oncall#13130`.
