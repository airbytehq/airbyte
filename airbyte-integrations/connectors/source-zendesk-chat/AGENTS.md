# Contributing to source-zendesk-chat

For general guidance on contributing to Airbyte connectors, see the [Connector Development documentation](https://docs.airbyte.com/connector-development/).

## Incremental Stream Considerations

The Zendesk Chat (Zopim) API offers incremental exports for high-volume endpoints (chats, agents, bans, agent_timeline) via the Incremental API, but Zendesk stops serving that API to third-party integrations such as Airbyte between 2026-12-02 and 2027-01-19 (see "Unique behaviors" below). The `chats` stream therefore reads through Search Chats plus List Chats since 2.0.0; `agent_timeline` still reads the incremental export because it has no replacement endpoint. The remaining FR parent streams are config-style lookups (accounts, departments, goals, roles, routing_settings, shortcuts, skills, triggers) that do not support date-based filtering.

## Unique behaviors

### 1. `chats` is a search-then-fetch substream, not a single endpoint read

Zendesk [stops serving the Incremental Exports API to third-party integrations](https://support.zendesk.com/hc/en-us/articles/11275429993498) between 2026-12-02 and 2027-01-19 (blocked requests return HTTP 403), and the only replacement for `incremental/chats` is the regular Chats API. Since 2.0.0 the `chats` stream is a substream of the internal `chats_search` parent (defined in `definitions.streams`, deliberately not listed under `streams`, so it never appears in the catalog). The parent calls [Search Chats](https://developer.zendesk.com/api-reference/live-chat/chat-api/chats/#search-chats) with `q=update_timestamp:[start TO end]` in 30-day windows from its cursor (minus a one-day lookback) to now, paginating with the `page` number taken from `next_url` (40 results per page). The child groups the ids found with a `GroupingPartitionRouter` (50 ids per group, the documented maximum of the `ids` parameter) and calls [List Chats](https://developer.zendesk.com/api-reference/live-chat/chat-api/chats/#list-chats) with `ids=`, whose response is a `docs` map keyed by chat id, hence the `["docs", "*"]` extractor path. Groups span search windows, so a group can contain ids from several windows. An id that List Chats no longer has (a chat deleted between the search and the fetch) comes back as `"<id>": null` with HTTP 200; the child's `record_filter` drops those nulls, which would otherwise fail schema normalization and the sync. A 404 is ignored on every other stream, but both requests of `chats` fail the sync on it (`system_error`) through their own error handlers, because neither has a missing record to answer 404 for. An ignored search window would close as empty and let the state move past the chats updated in it once a later window returns chats. An ignored `ids=` fetch would close the group as an empty partition (verified live: List Chats answers unknown ids with HTTP 200 and null documents), drop up to 50 chats and let the parent state move to the end of the last window that found one of them.

The two cursors differ. The child's cursor is `timestamp` (the chat start time), the cursor field users see. The parent's cursor is `search_window_end`, a field the connector stamps on every search result with `AddFields` from `stream_interval['end_time']`; each half of a split window stamps its own end, and the field never reaches a `chats` record because the child emits the List Chats documents. The search filter is `update_timestamp`, so the parent state is a point in update time like the filter, and each sync restarts one day before the end of the last window that returned chats. A parent cursor on `timestamp` would restart one day before the newest chat started and re-emit every chat updated since then on every sync, without bound on an account where new chats stop but old ones keep being updated. `update_timestamp` itself is in neither the Search Chats nor the List Chats payload, so it cannot be the cursor; `deleted`, `update_timestamp` and `engagements` only exist in the incremental export and were dropped from the schema. The `ChatsStateMigration` component converts the pre-2.0.0 state (`{"update_timestamp": <epoch seconds or ISO>}`) into the global-cursor shape, seeding the child's `timestamp` and the parent's `search_window_end` with the old value (both the old value and the parent cursor are update times), so upgrades resume without a re-read from `start_date`.

Search Chats returns at most 10,000 results per query (page 251 is a 400), so the parent's error handler resolves a first page whose `count` is 10,000 or more to `SPLIT_REQUEST_WINDOW` (`>=` because Zendesk does not document whether `count` is capped) and the retriever's `request_window_splitting` halves the window; after the CDK's ten split levels the floor is about 42 minutes (30 days / 1024), and more than 10,000 chats updated inside a window at that floor fails the sync explicitly. The window size is a manifest constant (`step: P30D`). `update_timestamp` is not in Zendesk's list of documented searchable fields; it filters correctly today (verified live: server-side, inclusive bounds at one-second precision), but an unknown field returns HTTP 200 with `count: 0`, so if Zendesk ever drops it the stream silently syncs nothing while the sync stays green. The per-sync request budget is one search per 30-day window plus one per additional page of 40 results, plus one List Chats request per 50 ids; an account without new or updated chats still pays one search per 30 days of range since the last window that returned chats, because the CDK's state follows the cursor values of records and an empty window emits none (verified live: 37 searches and 0 records on a sync three years after the last update). The one-day `lookback_window` makes a sync re-emit the chats updated during the day before the parent state (the export re-sent only the chats updated at the saved second); a chat that is not updated again is re-emitted for the last time by the first sync that starts more than a day after its last update. The lookback also repairs the one hole of page-number pagination (a chat pushed to the previous page by an update that lands between two page requests of the same window) for windows within a day of the parent state; a chat skipped this way in an older window of a backfill is re-read only after its next update. A 30-day window holds more pages than a one-day window did, so the exposure to that hole per window is wider.

**Why this matters:** Changing the search field, either cursor field, the window size or the group size changes which chats are re-read and how many requests a sync makes. Moving the parent cursor back to `timestamp`, or stamping anything other than the end of the window that returned the result, brings back unbounded repeats or lets the state pass chats that were not read. Ignoring a 404 on the search skips a window silently, and ignoring it on the `ids=` fetch skips a group of up to 50 chats silently. Filtering the child by its cursor (`is_client_side_incremental`) would drop updated chats whose `timestamp` is older than the state. Removing the state migration, renaming `chats_search` or renaming `search_window_end` breaks the resume for every connection upgraded from 1.x. Do not switch the parent to `timestamp` windows without a lookback that covers late updates. The window constant trades requests against the 10,000-result cap and the page-shift exposure: a larger window means fewer searches on long ranges but more pages per window and a higher floor after ten halvings; a window that holds 10,000 or more updated chats costs one extra search per halving.

### 2. `agent_timeline` still reads an incremental export and maps 403 to a configuration error

`agent_timeline` has no replacement endpoint in the Chats API, so it keeps calling `incremental/agent_timeline`. Zendesk did not list agent timelines in the shutdown announcement, so whether that export keeps working after 2026-12-02 is unknown. The stream uses a dedicated error handler (`definitions.incremental_export_error_handler`) that turns an HTTP 403 into a `config_error` naming the stream and pointing to the 60-day partner extension in Zendesk Admin Center; the export is also limited to the Owner and Administrator roles, so the message mentions the role as the other cause. The 403 mapping must stay limited to `incremental/` paths because other endpoints return 403 for ordinary permission problems.

**Why this matters:** Reusing the shared `error_handler` for this stream would surface the shutdown as a generic failure, and applying the incremental-export handler to other streams would mislabel permission errors. If Zendesk later confirms a replacement for agent timelines, move the stream off the export and delete the dedicated handler.
