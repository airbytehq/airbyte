# source-customer-io: Unique Connector Behaviors

## 1. The App API Is API-Key-Only

`definitions.base_requester` sends the App API key as a bearer token. That is the only scheme the twenty-two operations the connector calls accept: each declares `security: Bearer-Auth` with no required scopes in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json) ([authentication](https://docs.customer.io/integrations/api/app/#authentication)). Customer.io's OAuth 2.0 flow exists only for its MCP server ([auth.md](https://docs.customer.io/auth.md)), and `sa_live_` service-account tokens work only on the transactional send endpoints (`/v1/send/*`, `components.securitySchemes.ServiceAccount-Auth` in the spec). The Region field selects `https://api.customer.io/v1` or `https://api-eu.customer.io/v1`.

**Why this matters:** There is no OAuth flow to add for these endpoints. App API keys are not Track API keys ([Track vs App keys](https://docs.customer.io/accounts/settings/managing-credentials/#track-api-keys-vs-app-api-keys)) and are shown only once ([App API keys](https://docs.customer.io/accounts/settings/managing-credentials/#app-api-keys)). Customer.io does not redirect App API requests to the other region, so a wrong Region fails with 401 like an invalid key ([data centers](https://docs.customer.io/accounts/settings/data-centers/#specifying-your-region-in-the-api)).

## 2. HTTP Errors Are Classified on the Shared Base Requester

Every requester, including the parent copies inside the partition routers, `$ref`s `definitions.base_requester`, which carries one `DefaultErrorHandler`. The five substreams (`campaigns_actions`, `broadcast_actions`, `newsletter_variants`, `segment_usage` and `segment_memberships`) set `error_handler` to `$ref: "#/definitions/substream_error_handler"`, a `CompositeErrorHandler` that first ignores 404 and then applies the shared handler.

| Status | Action | Failure type | Meaning |
| --- | --- | --- | --- |
| 401 | FAIL | `config_error` | Invalid key, a Track API key, the wrong Region, or an IP address outside the allowlist; the message names each fix |
| 403 | FAIL | `config_error` | Access denied: a key whose scope excludes the data, or an IP address outside the allowlist; the message names both |
| 429 | RATE_LIMITED | `transient_error` | Over the 10 requests per second limit; retried |
| 500, 502, 503, 504 | RETRY | `transient_error` | Temporary server error; retried |
| 404 on a substream request | IGNORE | - | The parent automation, broadcast, one-time send or segment was deleted after the parent list was read, and its child records are skipped |
| 400 | FAIL (CDK default) | `system_error` | `listCampaignActions` and `broadcastActions`: invalid automation or broadcast ID; `listMessages` and `getPeopleById`: malformed request |
| Other | CDK default mapping | As mapped | For example 408 is retried and 405 fails; codes the CDK does not map are retried |

Retries wait for `Retry-After`, or fall back to `ExponentialBackoffStrategy` with factor 2 (4, 8, 16 s and so on) when the header is absent; the CDK adds one second to either wait. They stop after `max_retries: 30`, or when an attempt that started after the CDK's 600 s `max_time` fails: the CDK checks that limit only before each attempt and never shortens its own wait. A persistent 5xx, or a 429 without `Retry-After`, therefore fails after 9 attempts and about 17 minutes of waits (5, 9, 17 ... 513 s); with `Retry-After: 1`, `max_retries: 30` ends it after about a minute. The CDK defaults live in `airbyte_cdk/sources/streams/http/error_handlers/default_error_mapping.py`.

The [OpenAPI spec](https://docs.customer.io/files/journeys-app.json) documents 200 and 429 for `listCampaigns`, `listBroadcasts`, `listTransactional`, `listSenders`, `listSegments`, `getTopics`, `listWebhooks`, `getCollections`, `listActivities` and `getSuppressionByType`, 200, 400 and 429 for `listMessages` and `getPeopleById`, 200, 401 and 429 for `getObjectTypes` and `getPeopleFilter`, and only 200 for `listNewsletters`, `listWorkspaces` and `listSnippets`. Each substream operation also documents 404 for a parent that does not exist: [`listCampaignActions`](https://docs.customer.io/integrations/api/app/tag/automations/listcampaignactions/), [`broadcastActions`](https://docs.customer.io/integrations/api/app/tag/broadcasts/broadcastactions/), [`listNewsletterVariants`](https://docs.customer.io/integrations/api/app/tag/newsletter-variants/listnewslettervariants/), [`getSegmentDependencies`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentdependencies/) and [`getSegmentMembership`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentmembership/) (live, a missing segment returns 404); the first two also document 400 for an invalid ID. [`getPeopleById`](https://docs.customer.io/integrations/api/app/tag/customers/getpeoplebyid/) documents no 404: "If an ID in the request does not exist, the response omits it." A 429 carries `Retry-After` ([API rate limits](https://docs.customer.io/integrations/api/customerio-apis/#api-rate-limits)); the spec's header description adds that it is absent when a daily quota is hit, which is when the exponential backoff applies. `components.responses.Unauthorized` describes 401 as a missing or invalid API key.

**Why this matters:** Keep the filters on `base_requester` so every requester inherits them; `$ref` merging is key-level, so a per-stream `error_handler` replaces the shared one and loses the messages and the backoff unless it ends with `$ref: "#/definitions/base_requester/error_handler"`. Customer.io does not document which status a blocked IP address gets ([IP allowlist](https://docs.customer.io/accounts/settings/managing-credentials/#restrict-api-access-by-ip-address)), so both messages mention the allowlist. App API keys are created "with a defined scope" (`components.securitySchemes.Bearer-Auth` in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json)), so the 403 message also names the key's scope. Neither the spec nor [managing credentials](https://docs.customer.io/accounts/settings/managing-credentials/) lists the scopes a key can have or a 403 for the personal-data operations of `messages`, `activities`, `people`, `segment_memberships` and `esp_suppressions`, so whether a restricted key gets 403 there is unverified. Point every new substream at `substream_error_handler`: without it, a parent deleted mid-sync fails the sync with the CDK's 404 `system_error`. The `people` fetch does not use it: getPeopleById omits IDs it cannot find, and live a group with no known ID returned 200 with no one, so a 404 there fails the sync (CDK default `system_error`) instead of dropping up to 100 people silently. In that composite, the 404 handler repeats `max_retries: 30` because the composite reads `max_retries` from its first handler, and the shared handler stays last because the composite returns the last handler's FAIL, which keeps the 401 and 403 messages.

## 3. One Shared Request Budget and Three Workers

The manifest declares `concurrency_level` (`default_concurrency: 3`) and an `api_budget` with one `MovingWindowCallRatePolicy` of 10 requests per rolling second and `matchers: []`, so the policy covers every request. Most App API endpoints allow 10 requests per second ([rate limits](https://docs.customer.io/integrations/api/app/#rate-limits)) from one bucket per workspace that every App API call without its own limit draws from, writes included (`components.responses.InboxPreviewReadRateLimited` in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json)). Each substream sends one request per parent record, plus one per extra page of actions or members, so 1,000 one-time sends add about 100 s of `newsletter_variants` requests.

**Why this matters:** Leave `matchers` empty: an `HttpRequestRegexMatcher` does not interpolate `url_base`, so it cannot follow the Region host, and one bucket covers every endpoint anyway. The customer's own App API traffic draws from the same bucket, so 429s still happen; at `Retry-After: 1` each retry takes about 2 s, so 30 retries ride out about a minute of them. More workers cannot push a sync past the budget.

## 4. Incremental Sync Is Client-Side With a One-Hour Lookback, Except `messages`

Only `listMessages` filters by time ([OpenAPI spec](https://docs.customer.io/files/journeys-app.json)), so `messages` reads server-side windows of creation time (section 17). Of the other operations, `listCampaigns`, `listBroadcasts`, `listTransactional`, `listSegments`, `getTopics`, `getObjectTypes`, `listWorkspaces`, `listWebhooks`, `listSnippets` and `getCollections` take no parameters, `listCampaignActions` takes only the `start` page cursor, `listNewsletters` takes `limit`, `sort` and `start`, `listSenders` takes the same plus `hidden`, `broadcastActions`, `listNewsletterVariants` and `getSegmentDependencies` take only the parent ID, `getSegmentMembership` takes the segment ID, `start` and `limit`, `listActivities` filters only by type, name or person, `getPeopleFilter` only by segment or attribute (`eq` or `exists`), `getPeopleById` takes IDs, and `getSuppressionByType` takes `domain`, `limit` and `offset`. Every other incremental stream therefore sets `is_client_side_incremental: true`: each sync reads the full lists (`activities` stops early, section 18) and emits records whose cursor (epoch seconds, `datetime_format: "%s"`) is at or after the saved cursor minus `lookback_window: PT1H`. `start_datetime.max_datetime` caps the start at the current time, so a future Start Date passes the check instead of failing it; until that date a sync emits only records edited while it runs.

`campaigns_actions` and `broadcast_actions` keep one cursor per parent, and the CDK starts a new parent's partition from the stream-wide cursor minus the previous sync's duration, then applies the lookback (`airbyte_cdk/sources/declarative/incremental/concurrent_partition_cursor.py`). The spec documents no update-time field for the ten full refresh streams: it gives the last update time of variants and senders only inside the `id:timestamp` string `deduplicate_id`. `newsletter_variants` does return an undocumented `updated` (the timestamp in `deduplicate_id`), but client-side incremental would still request every one-time send's variants, would miss deleted variants, and could miss changes to the sender identity or layout values a variant resolves (`from`, `reply_to`, `layout`). Full refresh also drops deleted senders, and `segment_usage` has no timestamp: a segment's `updated_at` need not change when an automation starts using it. `collections` returns `updated_at` but is full refresh too (section 16). `people`, `segment_memberships` and `esp_suppressions` have none either: a profile's `timestamps` is deprecated and per attribute, membership has no time, and a suppression's `created` is when the address was suppressed. People who leave a segment and lifted suppressions disappear without a record, and all three page their whole list on every sync anyway.

**Why this matters:** The paginated lists are not ordered by their cursor, so a record edited after its page was read, while a later page holds a later edit, falls below the saved cursor; the lookback re-emits it on the next sync. Every sync re-emits the records updated in the hour before each saved cursor, until a newer edit moves the cursor: Append + Deduped absorbs them, Incremental | Append stores them as repeated rows. It costs no extra requests because every sync reads the full lists anyway; `activities` reads one more hour of activities. Actions copied into a duplicated campaign are skipped if they keep an `updated` older than that new-partition floor; Customer.io does not document whether they do. `transactional_messages`, `segments` and `snippets` use `updated_at`, and `activities` uses `timestamp`, not `updated`: a `cursor_field` the records lack turns the filter off with only a warning, because `ConcurrentCursor.should_be_synced` emits records that have no cursor value (`airbyte_cdk/sources/streams/concurrent/cursor.py`).

## 5. Substream Parents Are Inline Copies Without a Cursor

Each substream declares its parent inline in `partition_router`: a copy of the parent stream's requester, record selector, paginator (only `newsletters` has one) and schema `$ref`, without `incremental_sync`. In CDK 7.33.0 a parent that declares a client-side cursor filters its own records by Start Date even with `incremental_dependency: false`: `create_default_stream` wraps the parent's record selector in `ClientSideIncrementalRecordFilterDecorator`, and the parent gets an empty state manager, so its cursor starts at Start Date (`airbyte_cdk/sources/declarative/parsers/model_to_component_factory.py`). Saved child state never reaches the parent.

**Why this matters:** A `$ref` to the top-level stream, or a copied `incremental_sync`, silently drops every parent last updated before Start Date, and the child records of those parents are never requested, even when they changed later: a parent's `updated` does not follow its children (live, six of automation 1's seven actions were updated a day after the automation itself). For the same reason, do not set `incremental_dependency: true`, which would skip unchanged parents on every sync. When a parent stream's retriever changes, copy the change into its inline parent.

## 6. Action IDs May Arrive as JSON Strings

The API returns `campaigns_actions.id` as a JSON string (for example `"18"`) and the schema declares `string`, although the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json) documents an integer; `campaigns.actions[].id` arrives as an integer. [`broadcastActions`](https://docs.customer.io/integrations/api/app/tag/broadcasts/broadcastactions/) returns the same four action variants (email, SMS, WhatsApp, webhook), and the test workspace has no broadcast to show how it serializes `id`. So `broadcast_actions` declares the documented integer and applies two `AddFields` transformations. The first sets `broadcast_id`, half of the primary key, from the partition: the spec declares it on every variant, but live `listCampaignActions` records omit their documented `broadcast_id`. The second casts `id` with `value_type: integer` only when the API sends one (`condition: "{{ record.get('id') is not none }}"`): `"18"` and `18` both become `18`, and a null `id` stays null.

**Why this matters:** Joins between `campaigns.actions[].id` and `campaigns_actions.id` need a cast, and changing the declared type of an existing field is a breaking change, so `campaigns_actions.id` stays a string. Keep the `broadcast_actions` cast until a live read shows integer IDs; without it, string IDs would not match the declared integer.

## 7. Language and A/B Variants Are Separate Records

[`broadcastActions`](https://docs.customer.io/integrations/api/app/tag/broadcasts/broadcastactions/) returns an object for each language variant of a multi-language message, all with the same `multi_language_branch_action_id`, and each variant has its own action `id` ("To retrieve metrics for a single language variant, pass the `id` of the action", [`broadcastActionMetrics`](https://docs.customer.io/integrations/api/app/tag/broadcasts/broadcastactionmetrics/)). [`listNewsletterVariants`](https://docs.customer.io/integrations/api/app/tag/newsletter-variants/listnewslettervariants/) returns one object per variant of a one-time send, "a language in a multi-language one-time send or a test in an A/B test", each with its own `id`; `newsletters.content_ids` lists the same IDs. So `broadcast_actions` is keyed on `broadcast_id` and `id`, and `newsletter_variants` on `newsletter_id` and `id`, without `language`.

**Why this matters:** One message can arrive as several rows, one per language or A/B test. The per-variant broadcast action `id` is confirmed only by the spec, because the test workspace has no broadcast; if a live read shows variants that share an `id`, the `broadcast_actions` key needs `language`, which is a breaking change.

## 8. `sender_identities` Reads Visible and Hidden Senders and Ends on an Empty Page

[`listSenders`](https://docs.customer.io/integrations/api/app/tag/sender-identities/listsenders/) documents `hidden` as "If true, include hidden senders in the results", but live, `hidden=true` leaves visible senders out (checked on 2026-10-06: 0 senders with `hidden=true`, the workspace's one visible sender with `hidden=false` or no parameter; the workspace has no hidden sender, so what `hidden=false` does with hidden senders is unconfirmed). A `ListPartitionRouter` therefore reads `hidden=false` and `hidden=true` as two partitions, and a `record_filter` keeps each sender only in the list its own `hidden` flag belongs to, so `id` stays unique whatever the lists return. Each list pages with `limit=100` and `start` set from `next`, and stops when `next` is empty or absent or a page has no senders. The live API returns a non-empty `next` after the last sender (`"MQ=="` in the test workspace, the base64 of the last sender's ID), and the request with that token returns no senders and `next: ""`, so each list ends with one empty page.

**Why this matters:** Do not replace the partitions with `hidden=true` alone: that reads only hidden senders. The extra empty request per list is expected. Do not stop on `last_page_size < page_size` to save it: `limit` has no documented maximum, so a server-side cap below 100 would make full pages look short and end the read early without an error; the empty-page stop only guards against a stale token.

## 9. Archived Segments Are Not Synced

[`listSegments`](https://docs.customer.io/integrations/api/app/tag/segments/listsegments/) leaves out [archived segments](https://docs.customer.io/messaging/segmentation/segments/#archive-unarchive-a-segment), and `segment_usage` and `segment_memberships` call [`getSegmentDependencies`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentdependencies/) and [`getSegmentMembership`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentmembership/) for every listed segment, so none of the three streams has archived segments or their members. getSegmentDependencies returns one `used_by` object per segment (`segment_id` plus the IDs in `campaigns`, `draft_newsletters` and `sent_newsletters`), and the extractor emits it as one record keyed on `segment_id`; an empty or missing `used_by` yields no record.

**Why this matters:** Customer.io lets users archive a segment that is still used by archived automations or by one-time sends that already went out, so that usage is never synced. In incremental mode, a segment archived or deleted after a sync keeps its last version in the destination; Full Refresh | Overwrite mirrors the current list.

## 10. `campaigns_actions` Logs a Harmless Parent-State Warning

`campaigns_actions.retriever.partition_router` is a one-element list, so the CDK wraps the `SubstreamPartitionRouter` in a `CartesianProductStreamSlicer` and logs "Parent state handling is not supported for CartesianProductStreamSlicer." on every read. The other substreams declare `partition_router` as one object and do not log it.

**Why this matters:** The warning needs no action: the stream does not use parent state (there is no `incremental_dependency`), the parent `campaigns` list is read in full every sync, and the per-campaign cursors live in the stream's own state.

## 11. Four `campaigns` Fields Are Untyped

`audience.person_filters`, `audience.relationship_filters`, `object_attribute_triggers` and `relationship_attribute_triggers` are typed `object` in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json) (`paths./v1/campaigns.get` response, `campaigns.items.oneOf`), but every example there is a JSON string and no live record in the test workspace carries them, so the schema declares them without a type.

**Why this matters:** Do not type them `object` from the spec alone: if the API sends the JSON strings its examples show, typed destinations would null them. Type them once a live record shows the real shape; adding a type to an existing field is a breaking change.

## 12. `subscription_topics` Is Empty Until Topics Are Added

[`getTopics`](https://docs.customer.io/integrations/api/app/tag/subscription-center/gettopics/) returns an empty array when the workspace has no subscription topics. Topics are added in the workspace's subscription center, and the center can be enabled only after at least one topic exists ([enable the subscription center](https://docs.customer.io/messaging/channels/subscriptions/center/#enable-sub-center)), so the stream is empty in a workspace that never set up its subscription center, like the test workspace. `newsletters.subscription_topic_id` holds a topic `id` only when the subscription center is enabled (`newsletterObject` in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json)).

**Why this matters:** An empty `subscription_topics` is not a failure. A non-empty one does not mean the subscription center is on: topics are created before the center can be enabled, and `newsletters.subscription_topic_id` is set only once it is. The App API has no operation that creates topics or object types, so `subscription_topics` and `object_types` are `empty_streams` in `acceptance-test-config.yml` and only the unit tests read them. Topic IDs are integers in both streams, so `newsletters.subscription_topic_id` joins `subscription_topics.id` directly; `object_types.id` is a string ("Object type IDs are integers passed as strings", [`getObjectTypes`](https://docs.customer.io/integrations/api/app/tag/objects/getobjecttypes/)) while `campaigns.object_type_id` is an integer, so that join needs a cast.

## 13. `workspaces` Is a Snapshot of Account-Wide Counts

An App API key belongs to one workspace ([adding credentials](https://docs.customer.io/accounts/settings/managing-credentials/#adding-new-credentials)), but [`listWorkspaces`](https://docs.customer.io/integrations/api/app/tag/workspaces/listworkspaces/) returns every workspace in the account, three for the test key. `messages_sent` and `billable_messages_sent` count the current billing period, `people`, `objects` and `object_types` are current totals, and Customer.io caches the counts, so they can be up to two hours old ([OpenAPI spec](https://docs.customer.io/files/journeys-app.json)). The records have no update time, so the stream is full refresh only.

**Why this matters:** Each record holds the counts as of the sync, and the message counts cover only the current billing period, so only full refresh is meaningful: Full Refresh | Overwrite keeps the latest counts, and Full Refresh | Append keeps one snapshot per sync, dated by `_airbyte_extracted_at`. The test key, created for one workspace, lists all three workspaces of the account; Customer.io does not document whether a key with a narrower scope lists fewer.

## 14. `reporting_webhooks.endpoint` Can Carry Credentials

[`listWebhooks`](https://docs.customer.io/integrations/api/app/tag/reporting-webhooks/listwebhooks/) returns each webhook's `endpoint` URL as entered. A reporting webhook has no header or credential setting ([`createWebhook`](https://docs.customer.io/integrations/api/app/tag/reporting-webhooks/createwebhook/) takes only `name`, `endpoint`, `events`, `disabled`, `full_resolution` and `with_content`), so any credential the receiver needs is part of the URL: Customer.io documents basic authentication in the URL (`username:password@` before the host) as the way to secure one ([reporting webhooks FAQ](https://docs.customer.io/integrations/data-out/connections/webhooks/#frequently-asked-questions)), and a token can sit in the path or query string. An `AddFields` transformation removes the `username:password@` part with `regex_replace('(?i)(?<=^https://)[^/?#]*@|(?<=^http:/{2})[^/?#]*@', '')`. The pattern is anchored on the scheme, so an `@` later in the path or query, including one in a URL nested in the query, is kept; an empty or missing `endpoint` is left as is.

**Why this matters:** A token in the path or query string still reaches the destination, so the stream is not in `suggestedStreams`. `suggestedStreams` only sets the default selection of new connections: under Propagate all field and stream changes the platform selects every added stream and syncs it in the same job, and Autopilot rolls a release out with no user step (`autoStart`, `autoPromoteStages`), so connections with that setting sync the stream after their upgrade to 0.7.0; the user docs say how to stop it. The webhook signing key behind `X-CIO-Signature` is not in the response.

## 15. `snippets` Are Keyed by Name

[`listSnippets`](https://docs.customer.io/integrations/api/app/tag/snippets/listsnippets/) returns `name`, `value` and `updated_at`, with no ID. The [OpenAPI spec](https://docs.customer.io/files/journeys-app.json) documents `name` as unique, [`updateSnippets`](https://docs.customer.io/integrations/api/app/tag/snippets/updatesnippets/) creates or updates a snippet by `name`, and `deleteSnippet` takes the name in its path, so `name` is the primary key. A snippet cannot be renamed; a different name means a new snippet ([snippets FAQ](https://docs.customer.io/messaging/liquid/snippets/#frequently-asked-questions)).

**Why this matters:** A snippet copied to a new name arrives as a new record, and in incremental mode the old name keeps its last version in the destination after it is deleted; Full Refresh | Overwrite mirrors the current list.

## 16. `collections` Lists Metadata, Not Contents

[`getCollections`](https://docs.customer.io/integrations/api/app/tag/collections/getcollections/) returns each collection's `id`, `name`, `schema` (the top-level keys of its rows, which Customer.io does not enforce), `rows`, `bytes`, `created_at` and `updated_at`. The connector does not call [`getCollectionContents`](https://docs.customer.io/integrations/api/app/tag/collections/getcollectioncontents/), so no collection data is synced.

**Why this matters:** The stream shows which collections exist and how large they are, not what they hold. Customer.io does not document whether replacing a collection's contents changes `updated_at` (all four test collections have `created_at` equal to `updated_at`), so the stream is full refresh: incremental could keep stale `rows`, `bytes` and `schema`, and it would save nothing, because the whole list comes in one request and a workspace holds at most 50 collections ([collections](https://docs.customer.io/messaging/objects-data/collections/#create-a-collection)). Keep the contents out of it: they are free-form JSON rows, up to 10 MB per collection, with no fixed schema ([collections](https://docs.customer.io/messaging/objects-data/collections/)).

## 17. `messages` Reads 30-Day Windows of Creation Time and Re-Reads a Lookback

[`listMessages`](https://docs.customer.io/integrations/api/app/tag/messages/listmessages/) returns deliveries, one per message sent to one person, and filters them by creation time with `start_ts` and `end_ts`. It limits a request to 6 months: a longer range returns only 6 months, and a request without the bounds returns the latest 6 months. Customer.io documents no other retention for deliveries. `messages` therefore uses a server-side `DatetimeBasedCursor` on `created` with `step: P30D` and `cursor_granularity: PT1S`, so each window ends one second before the next starts. Both bounds are inclusive (live, 2026-10-06: a window with `start_ts` equal to `end_ts` returns the delivery created in that second), so no second is skipped or read twice. Each window pages with `limit=1000`, the documented maximum, and `start` from `next`, and ends on an empty `next`, which the last page returns. `type`, `metric`, `drafts` and the automation, one-time send and action filters stay unset, so sent deliveries of every channel are read and drafts are not.

`metrics` holds the time each metric was recorded, and it fills in after creation: live, `delivered` came about 8 hours after `created`, Customer.io records opens and clicks for 6 months after sending ([analytics](https://docs.customer.io/messaging/metrics/analytics/)), and it counts conversions up to 90 days after a delivery ([conversions](https://docs.customer.io/messaging/send/automations/conversions/)). So `lookback_window` is `messages_lookback_days` days, an optional config field (1 to 180, 30 when absent): each sync starts that far before the saved cursor, the highest `created` read.

**Why this matters:** Volume follows messages sent: 10 million deliveries take about 10,000 requests on the first sync, and every incremental sync re-reads one request per 1,000 deliveries created in the lookback, plus one per window. The default lookback is one window, which one worker pages alone, so high-volume workspaces may need a lower `messages_lookback_days`; metrics recorded after a delivery leaves the lookback arrive only with a larger value or a full refresh. Start Date applies to creation time, so a delivery created earlier is never synced, even if it is opened later. A blank Start Date starts at 0: about 690 empty windows since 1970 cost about 70 s on the first sync, and on every sync while the workspace has no deliveries, because the state moves only when a record is read. A future Start Date sends one window with `start_ts` equal to `end_ts` at the current time, which returns 200, so `max_datetime` stays. A deleted person's deliveries keep only `cio_id`, and a suppressed person's become anonymous ([delete people](https://docs.customer.io/messaging/send/recipes/delete-people/)), but rows synced before keep the address. `forgotten: true` means Customer.io did not keep the message content (`disable_message_retention` on a transactional send); what `subject` and `recipient` hold then is unverified. The schema adds `transactional_message_id` and `msg_template_id`, which the API returns but the `listMessages` response schema lacks. `metrics` declares no keys: they vary by channel and include keys the spec does not list (live `secondary:delivered`; `attempted` and `replied` in the reporting webhook events), and typed file destinations (S3 or GCS with Avro or Parquet output) drop undeclared keys.

## 18. `activities` Holds 30 Days and Stops at the First Page Outside the Cursor Window

[`listActivities`](https://docs.customer.io/integrations/api/app/tag/activities/listactivities/) is the workspace activity log: message events, tracked events, page and screen views, and attribute changes. It is "guaranteed to return activity history within the past 30 days" and has no time filter, sort parameter or documented order. `activities` is client-side incremental on `timestamp` with the one-hour lookback, sends `deleted=true` and `limit=100`, the maximum, on every request, and follows `next` into `start`. Its `stop_condition` ends the read on an empty `next`, on an empty page, or on a page that has no activity inside the cursor window (`last_page_size == 0`; in CDK 7.33.0 it counts only the records that pass the client-side filter) and whose last activity is dated before now. Live (2026-10-06, 25 activities), the list is newest first by `timestamp`, the last page returns `next: ""`, and `deleted=true` returns the same set as the default request.

**Why this matters:** The early stop keeps an incremental sync to the new activities plus one page. Paging the whole retained list instead emits nothing while it filters old pages, and the stream's state is emitted only when the read ends, so with `maxSecondsBetweenMessages: 1800` a sync would fail once 300,000 to 600,000 activities (3,000 to 6,000 sequential pages at the 0.3 to 0.6 s per request seen live) are older than the cursor, on every retry. The stop assumes the order is by `timestamp`, not by arrival, and an event's `timestamp` can be well before it is processed: backdated events, anonymous events merged when the person is identified, and processing delays ([activity logs](https://docs.customer.io/messaging/people/filtering-logs/)). A page of 100 such activities older than the window, listed above newer ones, ends the read and skips the newer ones; and, as with any client-side cursor, an activity more than an hour older than the previous sync's newest is never emitted incrementally. Keep the "dated before now" clause: the CDK drops activities dated after now, so without it a first page of 100 future-dated events would end every sync with no records. Keep `deleted=true`: `deleted` defaults to false, and a deleted person's activity stays attributed to their `cio_id` ([deleting people](https://docs.customer.io/messaging/people/manage/deleting-users/)); it does not narrow the list, so reading both values would fetch every activity twice. A connection that syncs less often than every 30 days loses the gap, and suppressing a person redacts their activity in Customer.io but not in rows already synced. Pages are read one after another, about 10,000 requests per million activities on a first sync. `data` is schemaless because its keys depend on the activity type; declaring some would make typed file destinations drop the rest.

## 19. `people` Searches Every Profile, Then Fetches 100 at a Time

`people` has no list endpoint. An inline parent, `people_search` (not exposed), calls [`getPeopleFilter`](https://docs.customer.io/integrations/api/app/tag/customers/getpeoplefilter/) (`POST /v1/customers`, `limit=1000`, `start` from `next`) with the body `{"filter": {"and": [{"attribute": {"field": "cio_id", "operator": "exists"}}]}}` and reads `identifiers`, not `ids`, which holds empty strings for people without an ID. A `GroupingPartitionRouter` (`group_size: 100`, `deduplicate: false`) over a `SubstreamPartitionRouter` on `cio_id` sends each group as `{"ids": [...]}` to [`getPeopleById`](https://docs.customer.io/integrations/api/app/tag/customers/getpeoplebyid/) (`POST /v1/customers/attributes?id_type=cio_id`), and each `customers[]` item is a record: the spec wraps the item's fields in `customer`, but live (2026-10-07) they are not wrapped. `AddFields` sets the primary key `cio_id` from `identifiers`, or from `attributes` when `identifiers` is absent as in the spec examples, with `value_type: string`. Both operations are reads; they use POST because the filter and the IDs travel in the body.

**Why this matters:** The search returns only people who match the filter. Every person has a `cio_id` that Customer.io generates and that cannot be removed ([identifying people](https://docs.customer.io/messaging/people/manage/identifying-people/#delete-person-identifiers)), so the filter matches everyone, while `id exists` would miss email-only people; the `and` form follows the spec's request example. Live (2026-10-07), the filter returned all 121 people of the test workspace, the same set as its all-users segment, `id exists` returned 119, and the filter's `not` returned none. `id_type=cio_id` for the same reason: `cio_id` is the only identifier every person has. The IDs go without the `cio_` prefix that listActivities asks for: live, prefixed IDs returned no one. getPeopleById omits IDs it cannot find, so a wrong `id_type`, ID format or record path reads no one and still succeeds: compare the record count with `workspaces.people` (121 in the test workspace), not only the status. Keep `deduplicate: false`, because the router's dedupe set would hold every `cio_id` of the sync (about 95 MB per million people), and `value_type: string`, or IDs like `30e00001` become numbers. `people_search` keeps its one-line inline schema: without a schema loader the CDK logs "Could not find schema" on every read. Full refresh only: the search has no time or range filter, and a profile has no update time. A sync costs ceil(N/1000) + ceil(N/100) requests, about 11,000 and at least 18 minutes at 10 requests per second for a million people. Every field is personal data: identifiers, every profile attribute (customer-defined keys, values stored as strings, kept as one free-form object), subscription preferences and device push tokens.

## 20. `segment_memberships` Has One Row per Person per Segment

[`getSegmentMembership`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentmembership/) returns a segment's members as `identifiers` (`cio_id`, `email`, `id`); the spec recommends them over `ids`, which lacks `cio_id`. `segment_memberships` reads it for every listed segment through an inline `segments` parent (section 5), adds the integer `segment_id` from the partition, and is keyed on `segment_id` and `cio_id`: a person belongs to several segments, and `id` or `email` can be null. It pages with `limit=30000`, the documented maximum, and `start` from `next`, and only an empty `next` ends a segment. Live (2026-10-06), `start` advanced without overlap, `limit=30000` returned all 121 members of "All Users" on one page with `next: ""`, matching [`getSegmentCount`](https://docs.customer.io/integrations/api/app/tag/segments/getsegmentcount/), and a missing segment returned the documented 404, which `substream_error_handler` skips.

**Why this matters:** The stream holds the sum of all segment sizes, often several times the people count, at about 90 bytes per member: 10 million memberships in 200 segments take at most about 735 requests. Membership has no timestamp and people leave segments without a record, so the stream is full refresh: Full Refresh | Overwrite keeps the current membership, and Append adds a full copy every sync. While a segment's `state` is `build`, Customer.io is still calculating who belongs to it (`segments.state` in the [OpenAPI spec](https://docs.customer.io/files/journeys-app.json)), so its rows can be out of date until a later sync. Do not stop on an empty page: `next` is an opaque position (`MDo2MQ==` is `0:61` after 5 members), so an empty page that still carries one is not proven last. A person who joins behind the current position during the read waits for the next sync. Each row ties an email address or ID to a segment defined on attributes or behavior, so it is personal data.

## 21. `esp_suppressions` Reads Each Suppression List per Sending Domain

[`getSuppressionByType`](https://docs.customer.io/integrations/api/app/tag/esp-suppression/getsuppressionbytype/) lists the addresses Customer.io's email service provider suppressed for one reason. Two `ListPartitionRouter`s cross the four types (`bounces`, `blocks`, `spam_reports`, `invalid_emails`) with the domains in the optional `esp_suppression_domains` field, sent as `domain`. Without domains the list falls back to `['']`: one partition per type, and the CDK does not send an empty value. `AddFields` adds `suppression_type` and `domain` (`""` when none is configured), which the records lack, for the key `[suppression_type, domain, email]`. The response has no `next` or total, so `OffsetIncrement` pages with `limit=1000`, the maximum, and `offset`; a page shorter than 1,000 ends a partition, as does `suppressions: null`, which an empty list and an offset past the end both return. Live (2026-10-06), `offset` advanced without overlap in email order, an offset past the end returned `suppressions: null`, the workspace's sending domain returned the same suppressions as no domain on all four lists (2026-10-07: 17,797 bounces, 24 spam reports), and an unknown domain returned 200 with no suppressions.

**Why this matters:** Customer.io suppresses an address on the domain where it bounced or was reported as spam ([suppression lists](https://docs.customer.io/messaging/channels/email/deliverability/esp-suppression/#sync-suppressions-across-domains)), the spec recommends "querying for each domain separately, as an email address may be suppressed on multiple domains", and no operation lists sending domains, hence the config field. Without it, an address suppressed on several domains may repeat under `domain: ""`; the test workspace has one sender identity, so this is unverified. Keep the `['']` fallback: an empty list would cross to zero partitions and read nothing. A mistyped domain reads as empty, not as an error. Delivery suppressions apply to every workspace that sends from the domain ([suppression based on message delivery](https://docs.customer.io/messaging/channels/email/deliverability/esp-suppression/#suppression-based-on-message-delivery)), so a list can hold addresses bounced in other workspaces: the test workspace sent 3 messages to internal recipients and lists at least 3,000 bounces. Only Customer.io's own email service provider keeps these lists; with a custom SMTP server the provider holds them ([view suppressions](https://docs.customer.io/messaging/channels/email/deliverability/esp-suppression/#esp-suppressions)), and what the endpoint returns then is unverified. A suppression added or lifted during a read can repeat or skip one row until the next sync. If deep offsets slow down on large lists, move the configured-domain partitions to the cursor-paged [`getDomainSuppressionsByType`](https://docs.customer.io/integrations/api/app/tag/esp-suppression/getdomainsuppressionsbytype/), which the vendor recommends for large datasets. Records hold end-user email addresses, and `reason` can repeat the address.

## 22. The Personal-Data Streams Stay Out of `suggestedStreams`

`messages`, `activities`, `people`, `segment_memberships` and `esp_suppressions` carry end-user data (sections 17 to 21), so none of them is in `suggestedStreams`, and new connections leave them unselected.

**Why this matters:** Keep them out when editing `suggestedStreams`. It only sets the default selection of new connections: a connection set up before 0.8.0 with Propagate all field and stream changes selects all five on upgrade and syncs them in the same job, with no user step under Autopilot (section 14), and the user docs say how to stop it.
